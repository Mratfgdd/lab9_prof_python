1. Постановка задачі, проєкт і тестові дані

Варіант 4. Система банківських рахунків. Створити 100 000+ рахунків і 500 000+ операцій, профілювати загальну суму коштів, оборот, статистику операцій і розрахунок балансу за великою історією; порівняти Python loops, NumPy та ProcessPoolExecutor; паралельно читати журнали операцій через ThreadPoolExecutor; змоделювати конкурентні поповнення/списання у спільній пам'яті з Lock. Проєкт продовжує ЛР1–ЛР8: правило ЛР1 (списання понад баланс відхиляється) і гроші в цілих копійках (ЛР7) збережено, тому результати всіх реалізацій порівнюються точно.

Досліджувана операція – пакетна обробка «кінця періоду» end_of_day: перерахунок балансів за всією історією з підсумковим звітом (загальна сума, оборот, кількість відхилених списань, середнє, стандартне відхилення і максимум сум) та нарахування 10 % річних зі щоденною капіталізацією й округленням до копійки (365 кроків на рахунок).

def apply_operation(balances: list[int], account: int, kind: int, amount: int) -> bool:
    if kind == WITHDRAW:
        if amount > balances[account]:
            return False
        balances[account] -= amount
    else:
        balances[account] += amount
    return True

def accrue_one(balance: int, days: int = DAYS) -> int:
    for _ in range(days):
        balance += (balance + HALF) // DAILY_DIVISOR
    return balance

def report_python(opening: Sequence[int], operations: Iterable[Operation]) -> LedgerReport:
    balances = list(opening)
    accepted: list[int] = []
    deposits = withdrawals = rejected = 0
    for account, kind, amount in operations:
        if apply_operation(balances, account, kind, amount):
            accepted.append(amount)
            if kind == DEPOSIT:
                deposits += amount
            else:
                withdrawals += amount
        else:
            rejected += 1
    mean, std, maximum = amount_statistics(accepted)
    return LedgerReport(balances, total_funds(balances), deposits, withdrawals, len(accepted),
                        rejected, mean, std, maximum)

4. Реалізації оптимізацій

Threads і processes. Рахунки незалежні, тож роботу ділимо за рахунками: для відсотків – на порції балансів, для звіту – на шарди account % N (порядок операцій кожного рахунку зберігається, частини звіту зливаються з точних цілих сум). Функції воркерів лежать у модулі без NumPy, щоб процеси стартували швидше; у Windows процеси запускаються через spawn, тому код запуску – під if __name__ == "__main__".

def accrue_threads(balances: Sequence[int], workers: int, days: int = DAYS) -> list[int]:
    with ThreadPoolExecutor(max_workers=workers) as executor:
        parts = executor.map(partial(accrue_chunk, days=days), split(balances, workers))
        return [balance for part in parts for balance in part]

def accrue_processes(
    balances: Sequence[int], workers: int, days: int = DAYS, chunksize: int | None = None
) -> list[int]:
    chunk = chunksize or max(1, len(balances) // (workers * 4))
    with ProcessPoolExecutor(max_workers=workers) as executor:
        return list(executor.map(partial(accrue_one, days=days), balances, chunksize=chunk))

def report_multiprocessing(
    opening: Sequence[int], operations: Sequence[Operation], workers: int
) -> LedgerReport:
    openings, parts = _shards(opening, operations, workers)
    results: Queue[tuple[int, Partial]] = multiprocessing.Queue()
    processes = [
        multiprocessing.Process(target=_process_worker, args=(shard, openings[shard],
                                                             parts[shard], results))
        for shard in range(workers)
    ]
    for process in processes:
        process.start()
    # Спершу забрати всі результати: процес не завершиться, поки його дані в черзі не прочитано.
    collected = dict(results.get() for _ in processes)
    for process in processes:
        process.join()
    return merge(opening, [collected[shard] for shard in range(workers)])

NumPy. Відсотки рахуються 365 векторними кроками для всіх рахунків разом. Звіт векторизується так: після стабільного сортування за рахунком cumsum дає поточний баланс після кожної операції; рахунки, де він ніде не став від'ємним (97% рахунків з операціями), не мають відхилених списань, і їхній результат готовий; решту (3.8% операцій) перераховує короткий Python-цикл.

Synchronization і caching. Списання – «перевір, потім зміни», тому читання, перевірки і запис балансу утворюють критичну секцію під Lock. Виписка рахунку проходить увесь журнал, тож повторні запити кешуються lru_cache; будь-яка прийнята операція очищає кеш (cache invalidation), бо виписки стають застарілими.

# class SharedAccount (shared.py)
def apply(self, kind: int, amount: int) -> bool:
    with self._lock or nullcontext():  # критична секція: читання - перевірки - запис
        current = self.balance
        if not self._within_limit(amount):
            return False
        if kind == WITHDRAW:
            if amount > current:
                return False
            current -= amount
        else:
            current += amount
        self.balance = current
        return True

# class Ledger (ledger.py): self.statement = lru_cache(maxsize=1024)(self._statement)
def apply(self, account: int, kind: int, amount: int) -> bool:
    accepted = self._apply(account, kind, amount)
    if accepted:
        self.statement.cache_clear()  # cache invalidation
    return accepted

7. Аналіз результатів

Bottleneck – нарахування відсотків (accrue_one, 78% часу під профайлером), задача CPU-bound. ThreadPoolExecutor не допоміг за жодної кількості потоків (1.02× з 8): через GIL Python-байткод потоків виконується по черзі. ProcessPoolExecutor залежить від обсягу роботи: на 10 000 рахунків він повільніший за baseline (0.42× – запуск 8 процесів дорожчий за 0.15 с обчислень), на 100 000 – 2.56×, на 400 000 – 4.33×. Оптимум – 8 workers (2.75×); з 16 прискорення падає до 1.64×: старт кожного процесу (spawn) коштує більше, ніж дає додатковий паралелізм, до того ж 8 з 16 ядер цього CPU – повільніші E-ядра. chunksize = 1 (рахунок за повідомлення) у 4.8 раза повільніший за chunksize = 100. Найкращий результат – NumPy: 7.8× на 100 000 і 8.3× на 400 000 рахунків, бо 365 кроків виконуються для всіх рахунків одночасно в скомпільованому коді; пам'яті при цьому потрібно менше.

Для звіту за журналом процеси повільніші на всіх розмірах (до 0.76× на 2 000 000 операцій): обробка операції дешева, і серіалізація сотень тисяч кортежів коштує більше за саму роботу. Process + Queue ще повільніший: у Windows start() передає дані шарду через канал запуску і чекає, доки дочірній процес (після імпорту головного модуля) їх прочитає, тож процеси стартують по черзі; ProcessPoolExecutor спершу паралельно запускає порожніх воркерів. NumPy швидший у 2.07 раза, але лише якщо дані вже в масивах: перетворення списку займає 0.089 с, і разом виходить повільніше за baseline – масиви варто формувати одразу під час завантаження журналу. Для I/O-bound читання потоки ефективні при справжньому очікуванні (2.52× із затримкою сховища); з локального SSD час визначає розбір CSV (CPU), і потоки дають лише 1.07×. Lock усунув втрати й не додав помітних витрат (0.107 с проти 0.122 с без нього). Caching скоротив 500 запитів виписок з 5.85 до 1.45 с, але коректний лише з інвалідацією після кожної зміни. Для production доцільно залишити NumPy для відсотків і статистики, кеш виписок з інвалідацією і Lock для спільного стану.

Висновки

Для банківської системи (варіант 4) на даних до 400 000 рахунків і 2 000 000 операцій виконано профілювання (cProfile, tracemalloc), визначено bottleneck і порівняно baseline, ThreadPoolExecutor, ProcessPoolExecutor, multiprocessing.Process, NumPy та кешування з 5 повторами для 3 розмірів даних і 1–16 workers. Для CPU-bound нарахування відсотків отримано прискорення 7.8–8.3× (NumPy) і 2.56–4.33× (процеси, 100 000–400 000 рахунків), потоки його не прискорили; потоки корисні лише для очікування I/O, процеси – лише коли обчислення дорожчі за передачу даних. Lock усунув race condition, кеш – повторні обчислення. Правильність усіх реалізацій підтверджено 16 тестів.
